The status above rests on two classes of evidence. Do not cite the second as if it were the first.

- `python3 scripts/test_aws_customer_skill.py --skill-dir <path>` returned PASS 8/8 against each installed copy: `~/.claude/skills/`, `~/.hermes/skills/`, and `~/.kiro/skills/`.
- Those three copies are byte-identical for `SKILL.md`, `get-sts-token.sh`, `get-customer-credentials.sh`, `fitcloud-api.sh`, and `self-update.sh`. Version strings report 1.7.2.
- `bash` resolved from `PATH` is Homebrew 5.3.9. `aws`, `jq`, `python3`, and `curl` are executable. This is a property of **this** workspace, not of the framework: the skill's shell client needs Bash 4.3+, and a machine whose `PATH` resolves macOS `/bin/bash` 3.2 cannot run it. There the conformance test reports `PASS WITH WARNINGS` and both customer-account capabilities are `blocked` until the skill owner ships a portability fix.
- Four copies are installed (`~/.claude/`, `~/.hermes/`, `~/.agents/`, `~/.kiro/`) and all four are byte-identical.
- The `csg-login` marker resolves `SKILL_DIR` to `~/.kiro/skills/aws-customer-account-ops`. **That copy executes for every agent**, whichever agent starts the session — the marker lives in the single machine-wide `~/.aws/config`, so one `SKILL_DIR` per machine is structural, not a misconfiguration. Per-agent copies exist so each agent can load `SKILL.md`; they are not the execution path.
- `self-update.sh` enumerates installed agents and updates every copy in one run, so routine drift is handled. The residual failure window is a **partial** update (`N agents OK, M failed`) that leaves the marker pointing at a copy that did not update. Run the drift check in `agents/install-verification.md` after any update that reports a failure.
- Broker config file and FitCloud API key are present. Values were not read or printed.
- `python3 scripts/validate_workspace.py` returned PASS.

`.kiro/settings/mcp.json` at the next idle boundary without restarting the session.
